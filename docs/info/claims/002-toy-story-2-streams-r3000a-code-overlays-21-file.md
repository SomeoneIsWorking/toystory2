## Claim

Toy Story 2 STREAMS R3000A code overlays: 21 files hold 245,148 bytes = 29.1% of the games code-bearing bytes, and the only other file on the disc holding a MIPS function epilogue is FMV/FMV.BIN, whose class is UNRESOLVED

## Evidence

MEASURED 2026-08-12, FOUR independent signals, each with its denominator; the count and the byte total were RE-MEASURED 2026-08-12 after a review found them padded by one file (see CORRECTION below). THE SET, 21 FILES: LEVEL01..LEVEL10/LEVEL.BIN (10 files, 3,608-19,040 B), LEVEL01..LEVEL10/LEVEL1.BIN (10 files, 24-18,744 B; LEVEL07/08/09 are 24-byte stubs), BITS/MEMORY.BIN (63,312 B, the largest). A 22nd file bearing an overlay NAME, LEVEL00/LEVEL.BIN, is 4 bytes (04000000) — a placeholder holding no code, NOT scannable and NOT counted. Boot t_size is 595,968 B, so 245,148/(595,968+245,148) = 29.15%. CORRECTION, 2026-08-12: this claim previously read "22 files hold 245,152 bytes". Both halves were wrong in the same way — the enumeration above is 21 files, and 245,152 is reachable only by adding the 4-byte placeholder the sentence itself excludes. Re-measured from scratch/flat: the 21 enumerated files sum to 245,148 B exactly; +4 = 245,152. The 29.1% figure is unaffected (29.146% either way). SIGNAL 1+2+3, the three-signal census by megamanx4/tools/code_scan.py used UNMODIFIED (no fourth detector was written; its --selftest was run ON TS2 OWN DATA and passed both classes: POSITIVE = 64 KiB at pc0 reads 99.2% code-plausible / 20.20 jr-ra per 1k words, NEGATIVE = TOY2FMV/TT.STR reads 1.1% / 0). Denominator: 274 of the discs 300 files, 24.5 MiB read IN FULL. Result, re-measured 2026-08-12 file by file and CORRECTED: 23 of 274 files contain at least one jr-ra, and the 23 are the 21 code overlays, the boot exe itself, and FMV/FMV.BIN (68 jr-ra) — whose class is UNRESOLVED (docs/re-frontier.md RE-04) and which is therefore NOT part of the overlay set. Every file OTHER THAN those 23 has ZERO. The earlier wording "the 22 overlays plus the boot exe itself; EVERY other file on the disc has ZERO" was false in both halves: it absorbed the one unresolved 510,960-byte file into the confirmed-overlay set, and it counted LEVEL00/LEVEL.BIN, which holds no jr-ra at all. The LEVEL*.BIN files read 74.6-98.8% code-plausible against the boot exe controls 92.4%. SIGNAL 3 is what kills the glyph-archive failure mode: 67.9-83.4% of each LEVEL*.BIN j/jal targets land INSIDE the boot exe .text (0x80010000..0x800A1800) against the boot exe own 91.5%, i.e. these modules are statically linked against the engine and call into it. That range covers the 16 LEVEL*.BIN files that contain any j/jal; the 4 stub LEVEL1.BIN files (LEVEL06 624 B, LEVEL07/08/09 24 B) have ZERO j/jal and are NO EVIDENCE either way. BITS/MEMORY.BIN is its own figure and is BELOW the LEVEL band: 423/836 = 50.6% — still nothing like the 0% of the PATH*.BIN trap case, but not inside 67.9-83.4%, and the generalisation must not be stated over it. THE TRAP DULY SHOWED UP AND WAS REJECTED: PAD/PATH*.BIN read 48.9-87.2% code-plausible with ZERO jr-ra and ZERO j/jal — waypoint coordinates whose bytes decode as legal instructions. Per-word decode separates them cleanly (LEVEL02/LEVEL.BIN 95.8% with 10 addiu-sp prologues vs PATH01.BIN 56.8% with 0, GFX/LOADING.RAW 53.8% with 0, LEVEL01/LEVEL01.VB 53.9% with 0, CHARS/BUZZ.ALL 41.7% with 0). SIGNAL 4, THE FORMAT IS VISIBLE IN THE BYTES: every LEVEL*.BIN opens with a u32 count then code; the 24-byte stubs are literally count, two jr-ra+nop no-op functions, 0xFFFFFFFF terminator; LEVEL06/LEVEL1.BIN (624 B) ends with a table of absolute addresses 0x800D1334/0x800D1420/0x800D12F4 terminated by 0xFFFFFFFF; BITS/MEMORY.BIN opens with the word 25 followed by 11 consecutive absolute address words; the meaning of the initial 25 is not inferred from that prefix. Independent corroboration from the boot exe itself, with each string re-located EXACTLY (mapping VA = file offset - 0x800 + 0x80010000): a 12-byte-stride table at file 0x13784 holds level1.bin @0x13784 = VA 0x80022F84, level2.bin @0x13790 = VA 0x80022F90, level3.bin @0x1379C = VA 0x80022F9C and level.bin @0x137A8 = VA 0x80022FA8 (each occurs exactly ONCE in the executable); 0x12518 holds the 15 directory stems plus bits-memory.bin; %s: not found sits at 0x13768 and %s: found at 0x13778. The earlier wording "the string table at file offset 0x13784 holds level.bin/…" was true of the TABLE but was elsewhere turned into "the level.bin string at VA 0x80022F84", which names the wrong slot — 0x80022F84 is level1.bin. WHAT WAS LOOKED FOR THAT WOULD HAVE SHOWN THE OTHER (megamanx4) ANSWER AND WAS NOT FOUND: a census where 0 of 274 files hold a jr-ra (got 23); base_fit reporting no fit for all 178 files (got 17 fits, 15 on one base with 0.0% runner-ups); no overlay filenames in the boot exe (found four). BLIND SPOTS, stated because the method cannot see past them: this asserts TS2 streams PLAIN absolutely-linked R3000A overlays and nothing else on the disc is plain code — it CANNOT assert there is no other code on the disc, because compressed or packed code reads as data; 26 files / 525 MB of TOY2FMV was never scanned (only TT.STR, as the selftest negative), so the denominator is 274 of 300 and unmeasured is not absent; fragments under 64 bytes are invisible by construction.

## What would falsify it

a Ghidra decompile of the loader showing the LEVEL*.BIN files are interpreted data rather than executed code; or FMV/FMV.BIN (510,960 B, 68 jr-ra, class UNRESOLVED per RE-04) turning out to be a 22nd code overlay, which would change both the set and the 245,148 B total; or a census of the 26 unscanned TOY2FMV files (525 MB) finding plain code in them; or any LEVEL*.BIN turning out to be a relocated module rather than absolutely linked, which would change what the j/jal-into-.text signal means
