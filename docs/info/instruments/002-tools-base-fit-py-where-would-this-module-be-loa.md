## Instrument

tools/base_fit.py — WHERE would this module be loaded? (the overlay load-base fit)

## Validated by

Validated in BOTH directions on real data 2026-08-12 by --selftest, real output: POSITIVE = the 10 LEVEL01..LEVEL10/LEVEL.BIN overlays, all 10 fit a base and EXACTLY 9 of them fit 0x800D1000 with 75-100% of their own out-of-.text jal targets inside the window against a 0.0% runner-up (the tenth, LEVEL09, peaks at 0x800D2000 with 66.7% of only 12 targets and a 33.3% runner-up - reported as-is, not smoothed). A DERIVATION GATE was added 2026-08-12 after review and it is the reason the reported BASE VALUE may now be trusted at all: three assertions a hardcoded base cannot satisfy - (a) exactly POS_AT_SLOT=9 at the slot AND LEVEL09__LEVEL.BIN at 0x800D2000, so the one file in the corpus that DISAGREES with the recorded slot must keep disagreeing; (b) re-scoring at the base the tool PRINTED must reproduce the hit count it CLAIMED; (c) a decoy base one --step above the reported one must score strictly worse. Real output on the fixed tool: LEVEL04 claims 65/65 at 0x800D1000, re-scores 65, decoy 0x800D2000 scores 43; LEVEL09 claims 8/12 at 0x800D2000, re-scores 8, decoy 0x800D3000 scores 0. SELFTEST PASS, exit 0. NEGATIVE 1 = 150 .ALL/.RAW/.DAT asset files, 0 fitted; NEGATIVE 2 = the 5 PAD/PATH*.BIN files, which are the TRAP CASE (48.9-87.2% code-plausible bytes with ZERO j/jal), 0 fitted. Exit 0, SELFTEST PASS with 155 negatives rejected. It REFUSES (exit 2) when the corpus glob matches zero files, saying it fitted NOTHING and that this is not a no-overlays result, and REFUSES (exit 2) when the boot executable is absent - because without its .text range every jal target counts as out-of-.text and every file would appear to fit something. THREE NEGATIVES ARE DISTINGUISHABLE AND ALL THREE ARE PRINTED rather than collapsing into silence: no-out-of-.text-jal (NO EVIDENCE either way), scored-and-rejected (no fit), and too-short. The runner-up column is what makes a flat score landscape visible, and it is required to be at least one file-length away from the winner - adjacent 4 KiB bases overlap almost entirely, so a naive next-best-base would tie by construction and the margin test could never fire. PORTED from the throwaway version written during the disc survey: repo-relative paths (no machine paths), the boot .text range read from the PS-EXE header instead of hardcoded, and the selftest added - the original had none. It belongs in external/psxport/tools/port/ under the tooling-hoist decision, since the question is generic; it lives here because a game repo may not edit the framework. BLIND SPOTS printed on every run: PLAIN absolutely-linked code only (a relocated/PIC module has no absolute jal and reads as no-evidence); 4 KiB granularity by default, so a non-aligned base is reported at the aligned address below it (BITS/MEMORY.BIN is exactly that case); and a fit is evidence about ONE module in isolation, so it cannot decide whether two modules fitting one base are alternatives sharing a slot or two modules at two bases. C010/I009 now provide the exact instruction-derived LEVEL and MEMORY placements; this instrument remains trusted only for its coarse fitting question.

## Known failure modes

FOUND AND FIXED 2026-08-12 (adversarial review, reproduced here before fixing): --selftest could not distinguish a MEASURED base from a HARDCODED one, so the tree's headline claim ("0x800D1000 is re-derived from the bytes every run") had no negative control. Splicing `h1, b1 = scores[0][0], 0x800D1000` into fit() - report the recorded slot for every file while keeping the true argmax's hit count - printed "SELFTEST PASS" with 10/10 fitted and 10 at 0x800D1000. Cause: both negative classes gate the fit/nofit VERDICT, which is independent of the reported base, and the only positive assertion about the base was `len(at_slot) >= 5`, which a hardcode MAXIMISES. Fixed by the DERIVATION gate above; the same sabotage now exits 1 with 4 FAILs (10-not-9 at the slot, LEVEL09 no longer disagreeing, the re-score 7 vs the claimed 8, and the decoy scoring 8 >= the reported 7). GENERAL LESSON for any fitting instrument: gating the VERDICT does not gate the VALUE, and a `>=` threshold on "how many agree with the recorded answer" is maximised by the failure it is supposed to catch. Note what was already properly gated and stayed that way: making `good` permissive fails with 144 assets fitting, and dropping the .text filter fails with 0/10 positives.
